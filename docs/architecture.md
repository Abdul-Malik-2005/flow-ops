# FlowOps — Архитектура и технические решения

## 1. Общая архитектура платформы
- **Домен:** Микросервисная платформа заказов, склада, оплат и уведомлений.
- **Порядок разработки:** Inventory (готов) → Identity (в работе) → Order → Catalog → Payment → Notification.
- **Изоляция данных:** Каждый сервис владеет своей БД PostgreSQL. Прямые запросы в чужие таблицы запрещены.
- **Взаимодействие:** Order использует async-оркестрацию через RabbitMQ + Transactional Outbox. Синхронные межсервисные вызовы (например, Order → Inventory) используют отдельный сервисный токен/заголовок, а не пользовательский JWT.
- **Ограничения:** Без Kafka, Kubernetes и Service Mesh.

---

## 2. Инфраструктурные правила и грабли (Lessons Learned)
- **Poetry:** Версия в `Dockerfile` (`ENV POETRY_VERSION=2.4.3`) должна строго совпадать с локальной. Любое изменение `pyproject.toml` требует `poetry lock`.
- **SQLAlchemy + PostgreSQL Enum:** Всегда использовать `StrEnum` и передавать `values_callable=lambda x: [e.value for e in x]` в `SAEnum`, иначе SQLAlchemy сохранит `.name` (`ADMIN`) вместо `.value` (`admin`).
- **Alembic `downgrade`:** Автогенерация не создаёт `DROP TYPE` для нативных enum. Дописывать вручную `sa.Enum(name='<type>').drop(op.get_bind(), checkfirst=False)` строго **после** `op.drop_table(...)`.
- **Pydantic Settings в тестах:** `pydantic-settings` ищет `.env` от `cwd`. В `tests/conftest.py` обязательно задавать `os.environ.setdefault(...)` **до** импорта модулей `app.*`.
- **Кэширование ключей в тестах:** Функции загрузки ключей обернуты в `lru_cache`. В фикстурах тестов обязательно вызывать `.cache_clear()` до и после теста.
- **Ruff:** В `pyproject.toml` исключать `migrations/versions` через `extend-exclude`. Использовать `datetime.UTC` (правило `UP017`).

## 3. Архитектурные решения: Inventory Service (Завершён, не менять)
- **Слои:** API → Service → Repository → Models. Репозитории не делают `commit`/`rollback` — границами транзакций управляет сервисный слой.
- **Конкурентность и идемпотентность:** Идемпотентность по `order_id` через PostgreSQL advisory lock + `SELECT ... FOR UPDATE` на строках остатков.
- **Модели:** `Inventory` (составной PK), `Reservation` (`order_id` unique), `ReservationItem` (composite FK).

---

## 4. Архитектурные решения: Identity Service
- **Токены (RS256):**
  - Access JWT (TTL 15 мин): claims `sub, role, type="access", exp, iat, jti` + `kid` в header.
  - Refresh JWT (TTL 30 дней): claims `sub, type="refresh", exp, iat, jti` + `kid` в header (без `role`, при обновлении роль всегда читается из БД).
- **Безопасность:**
  - Пароли хешируются через `Argon2id` (t=3, m=64 MiB, p=4).
  - При логине с несуществующим email выполняется проверка против dummy-хеша для выравнивания времени ответа.
  - Попытки входа (`LoginAttempt`) записываются в отдельной транзакции до выброса исключения 401/403, чтобы аудит не откатывался.
  - При обнаружении повторного использования уже отозванного refresh-токена (reuse) отзываются **все** refresh-токены пользователя.
  - При старте приложения (`lifespan`) выполняется fail-fast проверка наличия PEM-ключей (кроме `ENVIRONMENT=testing`).
- **Схема БД Identity:**
  - `users`: `id` (UUID PK), `email` (unique, lower-case), `password_hash`, `role` (`user_role` enum), `is_active`, `created_at`, `updated_at`.
  - `refresh_tokens`: `jti` (UUID PK), `user_id` (FK `ON DELETE CASCADE`), `expires_at`, `revoked_at`, `replaced_by_jti` (без FK, audit-поле), `created_at`.
  - `login_attempts`: `id` (UUID PK), `user_id` (nullable FK `ON DELETE SET NULL`), `email`, `success`, `ip`, `created_at`.

## 5. Архитектурные решения: Order Service
- **Сага `order-first`:** `pending → reserved`; отмена разрешена только из `pending` (у Inventory нет `release`/`confirm`, сервис заморожен). `order_id` генерируется приложением **до** вызова Inventory — резерв идемпотентен по `order_id`, поэтому `pending` восстановим.
- **Схема БД Order:**
  - `orders`: `id` (UUID PK, из приложения), `user_id` (**без FK** — граница сервиса), `status` (`order_status` enum), `currency` (varchar(3) + CHECK ISO), `total_amount`/`request_hash`/`idempotency_key`/`inventory_reservation_id` nullable, `reservation_started_at`/`reservation_attempts` (lease и бюджет попыток реконсилера), `created_at`, `updated_at`.
  - `order_items`: FK `order_id` `ON DELETE CASCADE`, `quantity > 0`, `UNIQUE(order_id, product_id, warehouse_id)` (он же индекс по `order_id`), цены nullable.
  - `order_status_history`: append-only аудит, `from_status` nullable, `reason` varchar(64) (набор причин валидируется доменом, не БД).
- **Индексы `orders`:** partial unique `(user_id, idempotency_key) WHERE idempotency_key IS NOT NULL`; `(user_id, created_at DESC)`; partial `(created_at) WHERE status = 'pending'` для реконсилера.
- **Деньги:** только `Decimal` + `numeric(12,2)`; `total_amount = NULL` означает «цена неизвестна» (Catalog не существует), `0.00` запрещено как ложное утверждение.
- **Транзакционные границы саги (order-first):** TX1 — `INSERT pending` + запись истории, **commit**; затем HTTP-вызов `reserve`; TX2 — применить исход и `reservation_started_at`. Держать транзакцию БД открытой на время сетевого вызова нельзя (блокировки + пул), поэтому «неизвестный исход» — легальное состояние: заказ остаётся `pending`, клиент получает `202`, дальше его доводит реконсилер.
- **Идемпотентность создания:** ключ — заголовок `Idempotency-Key` (≤ 255), дедуп по partial-unique `(user_id, idempotency_key)`; `INSERT ... ON CONFLICT DO NOTHING` возвращает 0 строк → сервис делает `rollback` и читает существующий заказ: совпал `request_hash` → `200` + исходный заказ, не совпал → `409`. Хеш считается по канонизированному телу (дубли строк схлопнуты, порядок фиксирован, цены не участвуют).
- **Lease против гонки «cancel vs reserve»:** `reservation_started_at` — «вызов, возможно, в полёте». Отмена разрешена только если lease пуст или старше `RESERVATION_STALE_AFTER_SECONDS` (валидатор требует `>= 2 * INVENTORY_TIMEOUT_SECONDS`), сравнение времени — в SQL (`now() - make_interval(...)`), а не в Python. Отмена, выигравшая гонку, не откатывается: заказ не воскрешается, orphaned reservation уходит в лог как `error`.
- **Реконсилер (block 6) — отдельный процесс, не фоновая задача в API:** `python -m app.worker` из того же образа (compose-сервис `order-reconciler`, без портов/healthcheck и **без** JWT-ключа). Он сознательно не импортирует `app.main`: иначе процесс требовал бы `jwt_public_key`, который ему не нужен, и падал бы по чужой причине. Свой `httpx.AsyncClient` на процесс, `engine.dispose()` в `finally`, SIGTERM/SIGINT → «доделать пачку и выйти с 0»; `--once` печатает отчёт (smoke-test/cron).
  - **Claim-by-lease (TX1):** один `UPDATE ... WHERE id IN (SELECT ... WHERE status='pending' AND (lease IS NULL OR lease < now()-stale) ORDER BY created_at LIMIT n FOR UPDATE SKIP LOCKED) RETURNING *`, который сразу ставит `reservation_started_at=now()` и `reservation_attempts += 1`, затем commit. Транзакция короткая: HTTP-вызов идёт **после** коммита, блокировки на время сети не держатся; второй воркер на том же бэклоге не ждёт (`SKIP LOCKED`), а берёт следующие строки.
  - **Lease = мьютекс и backoff одновременно:** свежий lease означает «попытка в полёте», поэтому отдельной колонки `next_attempt_at` нет. Исход `unavailable` **ничего не пишет** — следующий заход возможен только после истечения окна, т.е. backoff бесплатный.
  - **Единый маппинг исходов:** `app/services/reservation.py` (`apply_terminal_outcome`, `fail_exhausted_reservation`) используют и сага, и воркер — ретрай не может привести заказ в состояние, отличное от первичной попытки. TX2 — отдельная транзакция на заказ (CAS `WHERE status='pending'`), поэтому один сбойный заказ не рушит пачку.
  - **Бюджет попыток:** `reservation_attempts` инкрементится в claim **до** HTTP-вызова, поэтому упавший воркер всё равно тратит попытку (самовосстановление через окно lease). Условие отказа — `attempts > RESERVATION_MAX_ATTEMPTS` (а не `>=`): так `max_attempts` — это реальное число HTTP-вызовов. После отказа заказ → `failed` + `reservation_unavailable` **без** финального вызова.
  - **Отмена, выигравшая гонку с ретраем:** CAS вернул 0 строк → `rollback`, заказ остаётся `cancelled`, `error`-лог с `order_id`/`reservation_id` (сток может быть зарезервирован — у Inventory нет `release`).
  - **Алерт без метрик:** `PENDING_ALERT_AFTER_SECONDS` (валидатор: `>= RESERVATION_STALE_AFTER_SECONDS`) — один `error`-лог за проход, если `count_pending_older_than(...) > 0`; состояние не меняется.
  - **Грабли:** `RESERVATION_STALE_AFTER_SECONDS` у API и воркера **обязан** совпадать, иначе один процесс работает со строкой, которую второй считает занятой; лимит попыток может скрыть реально созданный резерв (нет `release` — только ручная чистка); новые индексы не нужны — claim едет по существующему partial `(created_at) WHERE status='pending'`.
- **Outbox relay (block 7) — третий процесс того же сервиса:** `python -m app.outbox_relay` из того же образа (compose-сервис `order-outbox-relay`, без портов, healthcheck и секретов). Транспорт спрятан за портом `EventPublisherPort`: `LogEventPublisher` (logger `app.events`) или `RabbitMQEventPublisher`, выбор — `OUTBOX_PUBLISHER`. Релей не знает, какой адаптер стоит: `publish()` без исключения и есть «доставлено».
  - **Цикл = три транзакции:** TX1 claim (`UPDATE ... WHERE id IN (SELECT ... FOR UPDATE SKIP LOCKED)`, попытка списывается **до** публикации) → commit → публикация **вне транзакции** по каждому событию в `try/except` → TX2 `mark_published` (CAS `published_at IS NULL`, `False` = duplicate) одним commit на батч → TX3 `count_exhausted_unpublished`. Сеть никогда не вызывается под блокировкой строки.
  - **`lease` = мьютекс и backoff одновременно:** упавшая публикация **ничего не пишет**, поэтому строка становится доступной ровно после истечения `locked_at + lease`. Валидатор требует `OUTBOX_LEASE_SECONDS >= 2 * OUTBOX_RELAY_INTERVAL_SECONDS`: проход обязан уложиться в собственный lease, иначе вторая реплика переклеймит строку, которая ещё публикуется.
  - **Строки не удаляются:** `attempts >= OUTBOX_MAX_ATTEMPTS` выводит событие из claim-предиката (строгое `<`) и превращает его в dead letter. Пропущенное событие всегда можно починить руками.
  - **Dead letters: счёт не на каждом проходе.** `count_exhausted_unpublished` частичным индексом не покрыт (`attempts` в него не входит), поэтому читается только когда он мог измениться: первый проход инстанса, проход с `failed > 0`, уже ненулевой бэклог (иначе после ручной чистки предупреждение не погаснет) и не реже, чем раз в `DEAD_LETTER_RECHECK_PASSES=100` проходов — это верхняя граница «слепоты» к dead letter, созданному другим инстансом. ERROR пишется **на рост** числа, дальше — WARNING-напоминание раз в `DEAD_LETTER_REMINDER_PASSES=60`: иначе штатное состояние инцидента даёт 12 ERROR в минуту и настоящая авария в них тонет.
  - **`RelayReport(claimed, published, failed, duplicates, exhausted)` — единственная наблюдаемость, метрик нет.** `duplicates` логируются на INFO: при at-least-once это штатное следствие (второй релей успел раньше), а не ошибка оператора. WARNING — только `failed` и `exhausted`.
  - **Политика цикла:** дренаж без сна, только пока `published >= claimed * 0.5` (`DRAIN_MIN_PUBLISHED_SHARE`); одно условие ловит и полностью мёртвый транспорт (`published == 0`), и частичную деградацию (тормозящий брокер, одно битое событие в каждой пачке) — в обоих случаях WARNING + сон, потому что дренаж деградировавшего транспорта выжигает бюджет попыток всего бэклога за секунды и отправляет строки в dead letter. Пустая пачка (`claimed == 0`) всегда спит. Исключение прохода → `logger.exception` + сон + continue, причём сон **экспоненциальный** (`pass_backoff`: `interval * 2**(n-1)`, потолок `MAX_PASS_BACKOFF_SECONDS=300`): условие «БД лежит / миграция не применена» длится минутами, и ретрай раз в 5 с только топит лог. Счётчик сбрасывается первым успешным проходом.
  - **Graceful shutdown:** обработчик сигнала только переключает `asyncio.Event` (`call_soon_threadsafe`), решение об остановке принимает цикл — между проходами. В compose `stop_grace_period: 35s` = lease (30) + interval (5): это бюджет достижения безопасной точки, а не время работы. Батч на RabbitMQ ограничен `CONNECT_TIMEOUT_SECONDS=10` + `PUBLISH_TIMEOUT_SECONDS=5` на событие; при включении брокера в production бюджет `stop_grace_period` надо пересчитать под реальную длину батча.
  - **Грабли:** релей сознательно **не** зависит от `order-api` в `depends_on` (только `order-db: service_healthy`): если схемы ещё нет, проход падает, логируется и повторяется — процесс догоняет сам, а зависимость от чужого healthcheck сделала бы его заложником API. Все реплики релея обязаны использовать одинаковые `OUTBOX_*`. Для сигналов используется `signal.signal`, а не `loop.add_signal_handler` (последний не работает на Windows). Все четыре `OUTBOX_*` выписаны в compose явно, чтобы изменение дефолта в `Settings` не меняло поведение production молча.
- **Транспорт RabbitMQ (block 8) — второй адаптер за тем же портом:** `RabbitMQEventPublisher` на `aio-pika 10` (`connect_robust`), включается `OUTBOX_PUBLISHER=rabbitmq` + `RABBITMQ_URL`; дефолт остаётся `log`, и это не осторожность, а корректность: пока ни один консьюмер не привязал очередь, `mandatory=True` превращает каждое событие в неудачную публикацию и сжигает бюджет попыток всего бэклога.
  - **Контракт обмена:** один durable topic exchange `OUTBOX_EXCHANGE` (по умолчанию `order.events`) на сервис-продюсер; routing key = `event_type` (`order.reserved`). Консьюмер биндит `order.reserved` или `order.#` — тема и есть язык подписки, таблицы маппинга нет, новый потребитель не требует деплоя продюсера. Очередей продюсер не объявляет вовсе: имя очереди знает только её владелец, иначе добавление второго консьюмера требовало бы правки продюсера. По той же причине DLX/DLQ появится вместе с первой очередью (блок с консьюмером), а не сейчас.
  - **Владелец топологии:** exchange объявляет продюсер (идемпотентно), durable-очередь и биндинг — её владелец-консьюмер при старте; одна очередь = ровно один логический потребитель (иначе round-robin раздаст события разным сервисам), поэтому второй потребитель — вторая очередь и свой биндинг. Одну очередь с одинаковым именем, но разными аргументами, брокер отвергнет `PRECONDITION_FAILED` (406), поэтому «владелец очереди» — ровно один сервис. Центральная «топология как код» появится, когда консьюмеров станет несколько и возникнет риск рассинхрона деклараций.
  - **Машинно-проверяемый контракт:** `contracts/order-events.schema.json` (JSON Schema draft 2020-12) в корне репозитория — единственный артефакт, который читает чужая команда, не импортируя наш код. Закрыт по схеме: `additionalProperties: false` на конверте, `oneOf` по `event_type` (у `order.reserved` обязателен `inventory_reservation_id`, у терминальных — `reason`), `unevaluatedProperties: false` над `allOf` — это единственная форма «закрытого» payload: `additionalProperties` в базовой схеме отклонил бы поля, которые добавляет вторая ветка. `tests/test_event_contract.py` (`jsonschema` — dev-зависимость) проверяет саму схему через `check_schema`, гоняет через неё `encode_event` для всех типов событий **с** `FormatChecker` (по умолчанию форматы `uuid`/`date-time` не проверяются), ловит негативные кейсы (нет `inventory_reservation_id`, лишнее поле, не-UUID id) и сверяет `enum` схемы с `OrderEventType`: новый тип события падает в тесте, а не у консьюмера. Копия `encode_event` остаётся в сервисе — общий пакет `flowops-contracts` отложен: он потребовал бы path-зависимость и перевыпуск lock в каждом сервисе.
  - **Версионирование:** routing key — семантический тип без номера (`order.reserved`), версия — поле `schema_version` в конверте; подписка — явный allow-list конкретных ключей, а не `order.#`. Совместимое изменение (новое опциональное поле) = bump `schema_version`, старый консьюмер его игнорирует; несовместимое = **новый** тип (`order.reserved.v2`) с двойной публикацией на время миграции — в allow-list он не попадает, пока потребитель сам не подпишется, поэтому миграция становится явным решением консьюмера, а не тайным протеканием. Номер версии в routing key не ставится: ключ — это язык подписки, его менять нельзя.
  - **Гарантия:** `delivery_mode=PERSISTENT` + durable exchange + publisher confirms (`publisher_confirms=True`) + `mandatory=True` + `on_return_raises=True`. `publish()` возвращается только после `Basic.Ack`; `Nack`/`Reject` и отсутствие очереди (`Basic.Return`) — исключение `EventNotDelivered`, строка остаётся `published_at IS NULL` и вернётся по lease. Тихой потери не существует: «вернулось» ≡ «у брокера есть».
  - **At-least-once, а не exactly-once:** сообщение с потерянным confirm публикуется повторно, поэтому консьюмеры обязаны дедуплицировать по `message_id` (= `id` строки outbox). `connect_robust` восстанавливает соединение и канал, но публикации, упавшие во время падения брокера, **не переигрывает** — это корректно, потому что вызов бросил, а лизинг вернул строку.
  - **Poison message: DLX/DLQ закладывается вместе с первой очередью, а не после инцидента.** Пересоздать durable-очередь ради DLX-аргументов на живых сообщениях дорого (нужен drain и окно недоступности), поэтому `x-dead-letter-exchange`/`x-dead-letter-routing-key` задаются при рождении очереди. Дисциплина консьюмера: транспортная ошибка (не подключились) → `nack` + requeue; детерминированная бизнес-ошибка (валидно по схеме, но обработчик падает) → **не** requeue бесконечно (hot-loop и head-of-line blocking всей очереди), а ограниченный retry по `x-delivery-count` → финальный reject в DLQ. Переигрывание из DLQ — отдельная джоба после фикса. Граница ответственности: `mandatory=True` продюсера гарантирует «дошло до очереди или строка осталась непомеченной», DLQ — «не потеряно после получения»; это аналог outbox+lease на стороне потребителя.
  - **Первый консьюмер — read-only журнал в самом Order (`order_event_projections`).** Пока `services/inventory` менять нельзя, естественного межсервисного потребителя нет, поэтому механика консьюмера обкатывается на собственном сервисе: отдельная append-only таблица, PK = `event_id` (= AMQP `message_id`), вставка `ON CONFLICT DO NOTHING` делает повтор at-least-once доставки no-op. Консьюмер **никогда** не пишет в `orders`/`outbox_events` и не порождает событий (иначе `order.reserved` зациклится через брокер); его единственная обязанность — зафиксировать факт обработки. Настоящий межсервисный потребитель (Notification/Catalog) получит ту же очередь и тот же контракт, не меняя Order, — поэтому это не «разговор с собой», а read-side на общей шине (зачаток CQRS).
  - **Рантайм консьюмера — четвёртый процесс того же образа** (`python -m app.event_consumer`, compose-сервис `order-event-consumer`, без портов и healthcheck): при старте объявляет топологию своей очереди (durable **quorum** queue, DLX + DLQ, allow-list биндингов из `OrderEventType` — не `order.#`), причём exchange переобъявляется идемпотентно, чтобы консьюмер мог стартовать раньше продюсера. Инварианты: `commit` строго до `ack`; детерминированная ошибка (`EventHandlingError`) → `nack(requeue=False)` → DLQ; временная ошибка БД/транспорта → `nack(requeue=True)` с прерываемой паузой (`sleep_or_stop`), иначе лежащий Postgres даёт hot loop; `aclose()` → `engine.dispose()` во вложенном `try/finally`. `prefetch=1` в интеграционных тестах и дефолт 10 в проде: обработка в колбэке последовательная, prefetch — только буфер round-trip'ов.
  - **Грабли RabbitMQ 4 (проверено на живом `rabbitmq:4-management-alpine`):** `x-delivery-limit` у quorum-очереди **не** применяется к явному `nack(requeue=True)` — сообщение можно requeue'ить бесконечно (в эксперименте 1368 доставок, DLQ пуст). Брокер сообщает счётчик в заголовке `x-acquired-count` (на первой доставке отсутствует, дальше равен числу предыдущих acquirement'ов, то есть `+1` — номер текущей доставки); предел проверяет рантайм (`previous + 1 >= EVENT_CONSUMER_MAX_DELIVERY_COUNT`) и на последней разрешённой доставке делает `nack(requeue=False)` → DLX → DLQ. `x-delivery-limit` остаётся в аргументах как страховка (например, при крахе консьюмера с unacked сообщением), но не как рабочий механизм; счётчик берётся у брокера, а не из памяти Python, поэтому переживает рестарт. Проверять ack в интеграционных тестах надёжнее через закрытие консьюмера и глубину очереди (unacked вернулось бы), а не опросом `message_count` сразу после публикации.
  - **Флип `OUTBOX_PUBLISHER` (compose):** `rabbitmq` включён только после того, как появилась durable-очередь (её объявляет консьюмер при старте), поэтому `mandatory=True` больше не превращает каждое событие в неудачную публикацию. Код-дефолт остаётся `log`: он нужен для запусков без брокера (`pytest`, локальный `--once`) и не должен требовать `RABBITMQ_URL` от API. Прод-конфигурация читается из compose, где `RABBITMQ_URL` и `depends_on: rabbitmq` заданы явно. Сквозной `tests/integration/test_outbox_to_journal.py` доказывает, что коммит в outbox доходит до журнала ровно один раз, а `published_at` ставится только после confirm.
  - **Наблюдаемость консьюмера — периодический `consumer report`.** Аналог `RelayReport`, но за интервал: `processed` (новые строки), `duplicates` (штатное следствие at-least-once), `retried` (временная ошибка), `refused` (детерминированный отказ → DLQ) и `dead_lettered` (исчерпан бюджет доставок). INFO — одна строка раз в `EVENT_CONSUMER_REPORT_INTERVAL_SECONDS`, счётчики после отчёта сбрасываются (кумулятивные числа заставляли бы оператора вычитать строки, чтобы увидеть темп). Per-event логи переведены в DEBUG: на живой очереди INFO на каждое событие превращает устойчивое состояние в поток строк. При остановке `report(force=True)` дописывает последний интервал — SIGTERM не скрывает работу процесса.
  - **Переигрывание DLQ — отдельный инструмент, а не автоматика** (`python -m app.dlq_replay --limit N`): dead letter удаляется из очереди только после publish с confirm и `mandatory=True`; routing key берётся из `event_type` в теле (не из `x-death`, где лежит история прошлых маршрутизаций), а тело без `event_type` возвращается в очередь и останавливает прогон — угадывать маршрут нельзя. Заголовки брокера (`x-death`, `x-acquired-count`) не копируются, иначе новый consumer увидит исчерпанный бюджет доставок и сразу отправит сообщение обратно в DLQ. Коды выхода: 0 — всё переиграно, 2 — что-то осталось человеку (битое тело), 1 — брокер отказал в publish. Автоматического переигрывания нет: сначала чинится причина, иначе сообщение просто вернётся в DLQ.
  - **Ленивое соединение и таймауты:** соединение открывается на первом `publish()`. Сборка релея и `--once` на пустом outbox не делают I/O; недоступный брокер — неудачный *проход*, а не падение старта. `CONNECT_TIMEOUT_SECONDS=10`, `PUBLISH_TIMEOUT_SECONDS=5` (меньше lease 30 с: зависший publish обязан упасть внутри прохода). Соединение и канал переиспользуются на весь батч, декларация exchange идемпотентна и повторяется на новом канале, `asyncio.Lock` + двойная проверка не дают открыть второе соединение.
  - **`aclose()` — часть порта:** у транспорта есть время жизни, поэтому порт требует `aclose()` (иначе релею пришлось бы делать `isinstance`). Релей закрывает сначала транспорт, затем `engine.dispose()` во вложенном `try/finally`: упавший close не должен утечь пулом соединений и замаскировать причину остановки. `LogEventPublisher.aclose()` — no-op.
  - **Грабли:** `PublishError` — **подкласс** `DeliveryError`, поэтому `except PublishError` обязан идти первым, иначе «нет очереди» диагностируется как «брокер отказал». `DeliveryError`/`PublishError` нельзя сконструировать без настоящих AMQP-фреймов (`__init__` требует `Basic.Nack`/`Basic.Return`, `__str__` читает `frame`) — в тестах они собираются через `pamqp`, иначе фейк проходит там, где настоящий объект даже не приводится к строке. `_redact` маскирует только пароль: логин нужен для диагноза «под кем не пустили». `requires-python` обязан иметь верхнюю границу (`>=3.14,<4`): без неё poetry считает Python 4 поддерживаемым и отвергает пакеты с маркером `<4` (aio-pika).
  - **Тесты:** юнит — на фейковых exchange/channel/connection (`connect` инъектируется, `connect` отдаёт новое соединение на каждый вызов, иначе фейк скрыл бы баг переподключения). Живой брокер — `tests/integration/test_rabbitmq_publisher.py`, гейт `ORDER_RABBITMQ_IT=1` + `RABBITMQ_URL`, каждый тест на своём exchange `order.events.it.<uuid>` с зачисткой. Полный путь «строка outbox → релей → брокер → очередь» проверяет `tests/integration/test_outbox_relay_rabbitmq.py` на живых Postgres и RabbitMQ (очередь объявляет сам тест — он играет консьюмера; exclusive-очередь умирает вместе с каналом, exchange удаляется в teardown): happy path с двумя событиями и сверкой тела/`message_id`/routing key с сохранённой строкой, кейс «очереди нет» (`failed=1`, `published_at IS NULL`, затем binding + истёкший lease → доставка со второй попытки) и кейс «второй проход ничего не публикует». Грабли тестов: `Settings` читает реальное окружение (`_env_file=None` отключает только `.env`), поэтому тесты конфига обязаны чистить транспортные переменные через `monkeypatch.delenv` — иначе экспортированный разработчиком `RABBITMQ_URL` ломает проверку «адрес обязателен». Compose: `rabbitmq:4-management-alpine`, healthcheck `rabbitmq-diagnostics -q ping`, volume, порты только на localhost.
- **Клиент Inventory — единственная точка правды о статусах:** клиент **никогда не бросает** исключений на бизнес-ответы, а возвращает типизированный исход (`reserved`/`rejected`/`item_not_found`/`invalid_request`/`unavailable`); маппинг в HTTP делает API-слой. Транспортные сбои (`timeout`, `5xx`, `429`, битый `2xx`) не отменяют заказ — иначе клиент получал бы «отменено» из-за сетевого чиха.
- **Пагинация списка:** keyset по `(created_at, id)` (не `offset`), курсор — opaque base64url `created_at|order_id`, naive-таймстамп отвергается (`400`), запрос тянет `limit + 1` строку, чтобы отдать `next_cursor` без второго COUNT.
- **Карта ошибок API (Order):** один словарь `_ERROR_HTTP_STATUS` (доменное исключение → код): `OrderNotFound`→404 (и для чужого заказа — существование не подтверждаем), `OrderNotCancellable`/`OrderStateChanged`/`IdempotencyConflict`/`InsufficientStock`→409, `InventoryItemNotFound`/`InvalidOrder`→422, `InvalidCursor`→400, `InventoryRejected`→502. Транспортная недоступность Inventory — **не** ошибка: `202` + заказ остаётся `pending`.
- **Аутентификация API (Order):** access-токен проверяется **локально** (`kid` → подпись → `type == "access"` → `sub`), без вызова Identity и без таблицы `users`: `Principal(user_id, role)` — это только клеймы. Следствие: смена роли применяется со следующим access-токеном (TTL 15 мин) — осознанный компромисс «нет сетевого вызова на каждый запрос». `user_id` всегда берётся из `sub` через DI (`CurrentUserId`), **никогда** из тела запроса (закрывает IDOR на уровне зависимостей).
- **Семантика 401 в Order:** отсутствие заголовка, не-Bearer схема и любая ошибка токена → `401` + `WWW-Authenticate: Bearer`. Нужен `HTTPBearer(auto_error=False)`, иначе FastAPI отдаёт `403`. `detail` единый и неинформативный (причина остаётся в цепочке исключений/логах) — чтобы не давать оракул «истёк / битая подпись / чужой kid».
- **Грабли (проверено на практике):**
  - В Order принят `MetaData(naming_convention=...)`. Явный `name=` у `UniqueConstraint`/`Index` **перебивает** convention — для генерации имён имя не указывается.
  - `Index("order_id", "created_at")` трактует первую строку как **имя индекса**; нужен `Index(None, "order_id", "created_at")`.
  - Partial-индексы содержат литерал ('pending') в `WHERE` — при переименовании статуса индекс надо пересоздать той же миграцией.
  - Идемпотентный `INSERT` делать через `pg_insert(...).on_conflict_do_nothing(index_where=<тот же предикат>)`, а не `try/except IntegrityError`: пойманная ошибка оставляет сессию в состоянии aborted-транзакции, и «прочитать существующую строку для replay» в ней уже нельзя.
  - `HTTP_422_UNPROCESSABLE_ENTITY` в Starlette помечена deprecated → `HTTP_422_UNPROCESSABLE_CONTENT` (иначе warning в каждом прогоне тестов).
  - Новый FastAPI подключает роутеры лениво (в `app.routes` лежит `_IncludedRouter` без `path`): для проверки маршрутов использовать `app.openapi()["paths"]`, а не обход `app.routes`.
  - Миграция с native enum: `postgresql.ENUM(..., create_type=False)` + явный `.create(bind, checkfirst=True)` (иначе второе `create_table` пытается создать тип повторно), а в `downgrade` — `DROP TYPE` **после** `drop_table`.
  - `ALTER TYPE ... ADD VALUE` нельзя использовать в той же транзакции ⇒ добавление статуса делается миграцией в два шага.
  - Контроль расхождений моделей и миграций: `alembic check` (в CI — после `upgrade head`).

## 6. Бэклог технических решений (на будущие сервисы)
- **JWKS-эндпоинт:** Внедрить при появлении следующих сервисов, чтобы не раздавать публичный ключ через `.env`.
- **Rate Limiting:** Добавить защиту `/auth/login` (sliding window / token bucket) после внедрения Redis.
- **Маскирование 422 ошибок:** Настроить кастомный обработчик `RequestValidationError`, чтобы вычищать поле `input` с паролями из ответов и логов.
- **Стратегия миграций B:** При переходе на несколько реплик API за Nginx вынести `alembic upgrade head` в отдельный one-off контейнер (`restart: "no"` + `depends_on: service_completed_successfully`). Там же снимется неявная зависимость воркера и релея от порядка старта API: сейчас схему двигает только API, а остальные процессы просто терпят «таблицы ещё нет».
