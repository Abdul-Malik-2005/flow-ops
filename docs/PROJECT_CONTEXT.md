## 1. О проекте

**FlowOps** — платформа управления заказами, складскими остатками, платежами и логистикой для интернет-магазина.

Проект разрабатывается как серьёзная портфолио-работа Python Backend Developer уровня Middle+.

Основная цель — продемонстрировать не только умение создавать REST API, но и понимание:
- микросервисной архитектуры;
- проектирования баз данных;
- транзакций и конкурентного доступа;
- асинхронного программирования;
- межсервисного взаимодействия;
- обработки ошибок;
- идемпотентности;
- тестирования;
- контейнеризации и инфраструктуры;
- мониторинга и CI/CD.

## 3. Архитектура системы

Планируемые микросервисы:

### Identity Service
- регистрация и авторизация;
- управление пользователями;
- JWT;
- роли и права доступа.

### Catalog Service
- товары;
- категории;
- характеристики;
- информация о товарах.

### Inventory Service
- складские остатки;
- доступное количество товаров;
- резервирование товаров;
- подтверждение и освобождение резервов.

### Order Service
- создание заказов;
- управление жизненным циклом заказа;
- взаимодействие с Inventory Service;
- управление составом заказа.

### Payment Service
- обработка платежей;
- статусы платежей;
- взаимодействие с платёжным провайдером.

### Notification Service
- уведомления;
- обработка событий;
- отправка сообщений пользователям.

Каждый микросервис должен владеть собственной базой данных. Прямой доступ одного сервиса к базе другого запрещён.

Взаимодействие между сервисами будет осуществляться через API и брокеры сообщений в зависимости от сценария.

## 4. Архитектурные принципы

1. Каждый микросервис отвечает за собственную бизнес-область.
2. Каждый микросервис владеет собственной БД.
3. Бизнес-логика не должна находиться в API endpoints.
4. Репозитории отвечают за операции доступа к данным.
5. Сервисы отвечают за бизнес-логику и управление транзакциями.
6. Ошибки БД не должны напрямую раскрываться клиенту.
7. Критичные операции должны учитывать конкурентный доступ.
8. Повторные запросы должны корректно обрабатываться там, где требуется идемпотентность.
9. Для каждого сервиса предусматриваются автоматические тесты.
10. Архитектурные изменения должны быть согласованы с общей системой.

Он отвечает за складские остатки и резервирование товаров под заказы.

**Владелец данных об остатках и резервах — исключительно Inventory Service.**

Order Service не обращается напрямую к таблицам Inventory Service.

## 6. База данных Inventory Service

### Inventory

Отвечает за складские остатки.

Составной первичный ключ:

`(product_id, warehouse_id)`

Основные поля:
- product_id;
- warehouse_id;
- quantity_on_hand;
- quantity_reserved;
- created_at;
- updated_at.

Ограничения:
- quantity_on_hand >= 0;
- quantity_reserved >= 0;
- quantity_reserved <= quantity_on_hand.

Доступное количество:

`available_quantity = quantity_on_hand - quantity_reserved`

### Reservation

Представляет резервирование товаров под заказ.

Основные поля:
- id;
- order_id;
- status;
- created_at;
- updated_at.

Для `order_id` предусмотрено уникальное ограничение.

Статусы:
- RESERVED;
- CONFIRMED;
- RELEASED.

### ReservationItem

Содержит отдельные позиции резервирования.

Основные поля:
- id;
- reservation_id;
- product_id;
- warehouse_id;
- quantity.

Для ReservationItem предусмотрены внешние ключи к Reservation и Inventory.

# 7. Критические архитектурные решения Inventory Service

### Владение данными

Inventory Service самостоятельно управляет таблицами складских остатков и резервирований.

Другие сервисы не имеют прямого доступа к его БД.

### Транзакции

Бизнес-операция резервирования выполняется в рамках одной транзакции.

Используется:

`async with session.begin()`

Repository не выполняет самостоятельный commit или rollback.

Управление транзакцией находится на уровне Service.

### Конкурентный доступ

Для защиты остатков используется PostgreSQL:

`SELECT ... FOR UPDATE`

Строки Inventory блокируются в детерминированном порядке:

`ORDER BY product_id, warehouse_id`

Это помогает избежать взаимных блокировок при одновременном резервировании нескольких позиций.

### Атомарность

Резервирование нескольких позиций атомарное:

- если все позиции доступны — резервирование выполняется;
- если хотя бы одной позиции нет или остатка недостаточно — вся операция откатывается.

### Идемпотентность

Повторный запрос с тем же `order_id` не должен создавать новое резервирование.

Если резервирование уже существует, сервис должен вернуть существующий результат.

Уникальное ограничение на `order_id` защищает от появления нескольких резервирований для одного заказа.

**Известный нюанс:** текущая реализация ещё требует дополнительной защиты от гонки при одновременном создании резервирования с одинаковым `order_id`, особенно когда запросы не блокируют общие строки Inventory. Это отдельная задача для последующей доработки.

### Дублирующиеся позиции

Если в одном запросе несколько раз передана одна и та же комбинация:

`product_id + warehouse_id`

позиции объединяются с суммированием количества до проверки остатков.

### AsyncSession

Одна AsyncSession используется для одной бизнес-операции.

Нельзя одновременно выполнять несколько независимых asyncio-задач с одной AsyncSession.

# 9. Инфраструктура и настройки БД

PostgreSQL запускается через Docker Compose.

Известные параметры:

- Docker Compose service: `inventory-db`;
- Container: `flowops-inventory-db`;
- PostgreSQL: 17;
- Database: `inventory_db`;
- Database user: `inventory_user`;
- Port: `5432`.

Для локального запуска приложения используется подключение через `localhost` или `127.0.0.1`.

Для подключения контейнеров внутри Docker-сети используется имя сервиса `inventory-db`.

Пароли и другие секреты хранятся в `.env` и не должны попадать в Git или этот документ.

Для тестирования предусмотрена отдельная БД:

`inventory_test_db`

Тесты не должны изменять рабочую `inventory_db`.

# 10. Тестирование

Используем pytest, а не unittest.

Причины:
- удобная параметризация;
- fixtures;
- поддержка асинхронных тестов;
- интеграция с FastAPI;
- удобная проверка HTTP API.

Настройки pytest находятся в `pyproject.toml`.

```toml
[tool.pytest.ini_options]
testpaths = ["tests"]
asyncio_mode = "auto"
asyncio_default_fixture_loop_scope = "function"
```

Тестовая инфраструктура уже создана:
- `tests/conftest.py`;
- `tests/test_database.py`.

Первый тест проверяет подключение к тестовой БД через `SELECT 1`.

Следующий этап — тестирование бизнес-логики резервирования:
- успешное резервирование;
- недостаточное количество;
- отсутствующая позиция;
- повторный запрос;
- дублирующиеся позиции;
- конкурентные запросы;
- корректный rollback.
