# FlowOps — Project Context

## 1. Цель проекта

FlowOps — учебная backend-платформа для управления заказами, складскими остатками, оплатой и доставкой интернет-магазина.

Главная цель — научиться проектировать и разрабатывать надёжные backend-системы, решать проблемы конкурентного доступа, целостности данных, повторных запросов и взаимодействия между микросервисами.

Это не просто CRUD-приложение. В центре проекта — корректность бизнес-процессов и устойчивость системы к сбоям.

## 3. Целевая архитектура

- Identity Service — пользователи и авторизация.
- Catalog Service — каталог товаров.
- Inventory Service — складские остатки и резервы.
- Order Service — создание и жизненный цикл заказов.
- Payment Service — симуляция платежей.
- Notification Service — уведомления.

Инфраструктура: PostgreSQL, Redis, RabbitMQ, Kafka, Nginx, мониторинг и контейнеризация.

Каждый сервис отвечает за собственные данные. Другие сервисы не должны напрямую изменять его таблицы.

## 4. Ключевые инженерные задачи

1. Не допускать резервирования большего количества товара, чем имеется на складе.
2. Защищаться от конкурентных запросов.
3. Обеспечивать идемпотентность операций.
4. Не создавать дубли при повторной доставке сообщений.
5. Корректно обрабатывать временную недоступность сервисов.
6. Управлять отменой заказов и освобождением резервов.
7. Обеспечивать согласованность распределённых бизнес-процессов.
8. Проверять корректность работы автоматическими тестами.
9. Обеспечивать наблюдаемость и возможность диагностики ошибок.

## 6. Принятые архитектурные решения

- Inventory Service — единственный владелец данных об остатках и резервах.
- Для первого варианта Order Service обращается к Inventory Service по REST API.
- Для защиты остатков используются транзакции PostgreSQL и блокировки строк.
- При резервировании нескольких товаров операция должна быть атомарной: либо резервируются все позиции, либо ни одна.
- При блокировке нескольких строк нужно соблюдать единый порядок, чтобы уменьшить риск взаимных блокировок.
- Повторный запрос с тем же ключом идемпотентности не должен создавать второй резерв.
- Для асинхронных событий планируется RabbitMQ.
- Kafka предназначена для потоковой обработки и аналитики, а не для бездумной замены RabbitMQ.

## 7. Правила обучения

- Объяснять назначение кода до его написания.
- Не давать готовые большие файлы без необходимости.
- Реализовывать проект небольшими последовательными шагами.
- Объяснять архитектурные решения и альтернативы.
- Давать небольшие задания на понимание.
- Проверять ответы и исправлять пробелы.
- Не считать функцию реализованной, пока она не написана и не проверена.
- Не утверждать, что код работает, если он не запускался и не тестировался.
